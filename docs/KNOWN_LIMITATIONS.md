# Known limitations (we say these first, before the other team does)

Owner: Role 4. Updated at the end of every day. Each entry: what, why it matters, what we did about it, where the evidence is.

| # | Limitation | Why it matters | What we did / will do | Evidence |
|---|---|---|---|---|
| 1 | Shipment outcomes are **simulated**. The simulator is driven by real data (Open-Meteo weather, IMF PortWatch traffic and port size, NY Fed GSCPI; SIM v0.3), but shipment-level delay records are not public | Absolute accuracy is not production accuracy | Real drivers wired in (decision 0010); comparisons (model vs baseline) are the findings; every row is labelled `SYNTHETIC_CALIBRATED` | `data/raw/sim/SIM_CARD.md`, `docs/06_DATA_SOURCES.md` |
| 2 | Labels depend on the simulator's outcome model | A model could learn the simulator, not logistics | Hidden-factor noise; outcome labels; leakage tests; report skill vs baselines | `Stage01_ML/reports/eval_leakage_tests.json` (Day 1) |
| 3 | The system recommends, humans decide | No automated rerouting | `requires_operator_review: true` in every response; no execution code path | API tests |
| 4 | Stage 06 (agentic rerouting) is outside the five-day scope | Problem statement lists it | Documented as future work | `docs/00_PROJECT_BRIEF.md` |
| 5 | Small human-labelled sets (gold NER/urgency set, 100 hand-written summaries, small rater panel) | Wide confidence intervals | Report n and CIs; never over-claim | Stage 3-4 eval reports |
| 6 | The simulator still has **seasonal drift**: after Role 3 softened it (data v1) the critical share is 12% in train, 17% in val and 18% in test, and the monthly critical share still ranges from about 4% (Jun-Jul) to 20% (Feb, Apr, Oct, Dec) | Test is later in the year and harder than train, so scores are not comparable with a random split; a validation-chosen threshold is not guaranteed to be optimal on test | Keep the frozen chronological split (no reshuffling), report per-split class mix in `eval_metrics.json`, slice by month and by peak season, quote CIs from day-block bootstrap | `Stage01_ML/data/data_quality_report.json`, `Stage01_ML/reports/eval_metrics.json` (`split_class_mix`), `Stage01_ML/reports/eda_drift_report.json` |
| 7 | The Little's-law / flow-conservation acceptance check is not applicable: the merged simulator is the allowed fallback design (AR(1) congestion, no queueing model) | We cannot claim the data obeys conservation laws | Say "calibrated congestion simulation" not "physics-based"; compare models and baselines, not absolute accuracy | `data/raw/sim/SIM_CARD.md`, `tests/eval/test_sim_acceptance.py` |
| 8 | `dwell_time_hours` and `capacity_utilization_pct` alone reach AUC 0.89 / 0.88 for CRITICAL | A simple dwell rule is a strong baseline; model gains over it may look small | Always report the dwell-rule baseline next to every model; report skill versus it | `eval_leakage_tests.json` (single-feature ceiling) |
| 9 | The shuffled-label test is only a scoring sanity check (it cannot detect leaky features) | A green leakage report could be over-read | Leaky features are covered by the single-feature ceiling, which now reads Role 1's test feature matrix, so all 77 model inputs are checked (max AUC 0.917 < 0.95); the policy check (a) covers the model card | `Stage01_ML/reports/eval_leakage_tests.json` |
| 10 | Exact numbers depend on library versions: tree models trained with xgboost 3.4 / scikit-learn 1.9 give slightly different probabilities than Role 1's xgboost 3.1.3 / scikit-learn 1.8.0 | A teammate on newer libraries sees threshold 0.30 and 40.6 false alarms per 100 alerts instead of 0.32 and 38.1; same champion, same conclusion | Verified claims use Role 1's versions (listed in `model_card.json`); Role 3 to pin them in `requirements.txt` | `Stage01_ML/HANDOFF/04_evaluation_engineer.md` |
| 11 | The model reads the hourly node table (decision 0009). The strongest single input is the node's previous-hour inventory (AUC 0.917) | A new data feed the API depends on; if it stops, node-history inputs fall back to training medians and scores degrade | Only completed past hours are used (`lag_` rule); tests in `tests/data/test_node_context.py`; flagged here and in the API hand-off | `common/dataio/node_context.py`, `Stage01_ML/HANDOFF/05_integration_engineer.md` |
| 12 | Stage 2 v1.0 (29-30 Oct) baselines and ablations were not real methods (sine-offset "seasonal naive", fixed-blend "xgb_lag", invented intervals, ablations run on one model trained with the real graph) | Any number from that file would not survive a question | Stage 2 rebuilt and v1.0 numbers withdrawn: real baselines, separately trained ablations, shared split dates (decision 0011) | `docs/decisions/0011-stage02-forecasting-design.md` |
| 13 | Few bottleneck episodes in the Stage 2 test period: 13 eligible test episodes (9 in val) with the full 7-day look-back | Episode recall and lead time have wide intervals | Wilson 95% intervals on recall, IQR on lead time; validation numbers reported alongside; never quote recall without n | `Stage02_DL/reports/eval_lead_time.csv` |
| 14 | The real-data track forecasts daily ship COUNTS (port calls / chokepoint transits), not dwell or TEU throughput; LA and Long Beach are one PortWatch port (kept once); rail and DC nodes have no real series | It shows the architectures work on real data, not that dwell forecasts are accurate in reality | Say "real traffic counts" precisely; 23 of 27 nodes; separate file and target name (`activity`) | `Stage02_DL/data/data_quality_report.json` (real_track) |
| 15 | Stage 2 numbers depend on run mode: `--fast` (hidden 32, <= 10 epochs) vs full (hidden 64, <= 30 epochs) | A fast-mode result may understate the neural models (they were still improving at epoch 10) | `model_version` ends in `-fast` for fast runs; only full-run numbers become VERIFIED claims | `Stage02_DL/artifacts/model_card.json`, `training_curve.csv` |
| 16 | Simulated hourly dwell carries ~7% multiplicative sensor noise, so 1-hour-ahead errors are mostly noise | Skill at 1 h is limited by noise, not by the models | Report skill per horizon; the 24 h-168 h horizons and lead time are the headline | `data/raw/sim/SIM_CARD.md`, `eval_forecast_metrics.csv` |
| 17 | The graph model does not beat its own no-graph and shuffled-graph ablations (fast run: 0/10 cells better, sim and real track); plain LSTM/Transformer are better | We cannot claim "the network topology improves forecasts" | Report it first as a finding; Role 2's lead-lag analysis to explain it; re-check after the full run | `Stage02_DL/reports/eval_graph_ablation.csv`, `eval_real_graph_ablation.csv` |
| 18 | Episode recall under the simple rule (median crosses the line) does not separate models: persistence gets 12/13 through noise, with 71 false alarms | A recall number alone would flatter any model | Each model's alert rule is chosen on validation by warning cost; models are compared on that cost | `Stage02_DL/reports/eval_lead_time.csv` |
| 19 | `httpx`/`httpx2` are not in `requirements-dev.txt`, so API and model-picker tests skip on a fresh install; Stage 2 latency was measured without the HTTP layer | API regressions could pass CI unnoticed (a real POST /forecast bug was found by hand on 31 Oct) | Role 3 to add the packages and re-measure over HTTP | `Stage02_DL/reports/integ_latency.json` |
